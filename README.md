# Сервис регистрации на мероприятия

Локальный клиент-серверный сервис: организатор создаёт событие с лимитом мест,
участники регистрируются по email, получают билет и проходят чекин по коду.
При заполнении мест работает лист ожидания; организатор видит статистику live.
[Репозиторий на GitHub](https://github.com/Akbarbiinazar/registration-event-test-task).
Исходное [задание](docs/ASSIGNMENT.md), принятые
[решения и инварианты](project_spec.md), [план доказательств](docs/PROOF_PLAN.md)
и датированный [журнал работы](docs/DEVLOG.md) находятся в репозитории.

## Требования и запуск

- Node.js **22.13+ LTS или 24+**, npm, Docker с Compose v2 и браузер.
- Свободные порты: `3000` (API), `5173` (web), `5433` (PostgreSQL), `1025`
  (SMTP Mailpit), `8025` (Mailpit UI). E2E дополнительно использует `3100`
  и `5174`.
- Доступ к npm registry при первом `npm ci` и к загрузке Chromium при первом
  `npx playwright install chromium`. Docker должен быть запущен.

Из корня свежего клона:

```sh
npm ci
npm run db:up
npm run migrate
npm run dev
```

Откройте [web](http://localhost:5173) и [Mailpit](http://localhost:8025).
API отвечает на `http://localhost:3000/api/health`. `npm run dev` остаётся
запущенным в терминале. `.env` не обязателен: локальные значения заданы в
`apps/api/src/config.ts`, пример переопределений — в `.env.example`.
Миграции запускаются для баз `events` и `events_test`. Для остановки
контейнеров используйте `npm run db:down` (без удаления данных).

Главная страница показывает реальные события из БД. Чтобы наполнить её
семью демонстрационными событиями, выполните `npm run seed`: повторный запуск
не добавит дубликатов и не удалит существующие записи.

## Ручной демо-сценарий

1. На web создайте событие на одно место с датой через **2 часа**. Форма
   использует часовой пояс браузера; после создания сохраните секретную ссылку
   организатора — она показана один раз. Откройте её в первой вкладке.
2. Во второй вкладке откройте публичную ссылку. Зарегистрируйте два разных
   email: первый получит место и билет, второй попадёт в лист ожидания.
   Проверьте письма в Mailpit, а в первой вкладке — счётчики без обновления
   страницы. Повторная регистрация первого email не занимает ещё одно место.
3. Откройте экран чекина из вкладки организатора. Возьмите код из письма
   первого участника и введите его. Счётчик «Пришло» обновится live;
   повторный ввод покажет, что код уже использован.
4. Для демонстрации повышения создайте другое событие на одно место,
   зарегистрируйте два email и откройте ссылку отказа из письма первого.
   Ожидающий получит письмо с билетом; счётчики организатора обновятся.
5. На экране организатора перенесите событие на более позднее время.
   Подтверждённые участники и ожидающие получат письма со старой и новой
   датами; отказавшиеся письма не получают.

Для быстрого напоминания вместо четвёртой команды запуска используйте
`REMINDER_TICK_MS=10000 npm run dev` (или добавьте переменную в `.env`).
Создайте событие через 2 часа и зарегистрируйте участника. Письмо
«Напоминание о событии» появится в Mailpit после ближайшего тика планировщика
и отправщика. Первый тик выполняется при запуске API; обычный интервал без
переопределения — 60 секунд. Окно напоминаний — от 24 часов до начала события,
не включая момент начала. Повторный тик не создаёт второго письма в очереди.

## Проверки

После `npm run db:up` и `npm run migrate`:

```sh
npm run check
npm run test:proofs
npx playwright install chromium
npm run test:e2e
```

Для SMTP smoke оставьте `npm run dev` запущенным в отдельном терминале и
выполните `bash scripts/smoke.sh`. Он создаёт уникальное событие и адрес,
регистрирует участника и ищет письмо через API Mailpit. E2E запускает свои
API и web на портах `3100`/`5174` с базой `events_test`; dev-база `events`
не используется. [P1–P6 и фактические результаты](docs/PROOF_PLAN.md#статус-доказательств)
покрывают регистрацию, очередь, гонки, напоминание, чекин и перенос.

| Работает | Напоминание в окне 24 часов и перенос с письмами — [P4/P6](docs/PROOF_PLAN.md#статус-доказательств), `e2e/reschedule.spec.ts`; SMTP-путь — `scripts/smoke.sh`. |
| Ограничено | SMTP-доставка имеет семантику **at-least-once**: при падении после принятия письма SMTP, но до записи `sent_at`, возможен повтор. `dedup_key` гарантирует одну постановку письма в outbox, а не ровно одну внешнюю доставку; это [допущение A12](project_spec.md#2-допущения). |
| Ограничено | Создание события берёт часовой пояс браузера; выбрать другой пояс в форме нельзя. Открытое решение по UI записано в [DEVLOG](docs/DEVLOG.md#2026-10-09-0042--ui-03-форма-создания-события). |
| Не проверено | Удалённый CI для текущего локального коммита: последний подтверждённый запуск относится к прежнему SHA. Свежий локальный клон запустился с изолированными портами; запуск ровно с портами README остался непроверенным из-за конфликта `5433` с другим контейнером. Подробности в [DEVLOG](docs/DEVLOG.md). |
| Требует проверки | `npm ci` сообщил о 12 уязвимостях зависимостей; `npm audit --omit=dev --audit-level=moderate` сообщил 0 для production-зависимостей. Dev-зависимости нужно отдельно разобрать перед следующей сдачей или обновлением стека. |
| Не делали | Аккаунты, подтверждение email и реального почтового провайдера: для локального демо используются секретные ссылки и Mailpit. Масштабирование на несколько API-процессов и регистрация с закрытием по времени не входят в [принятый объём](project_spec.md#7-сознательно-не-делаем). |

Последние локальные результаты и состояние удалённого CI указаны в
[DEVLOG](docs/DEVLOG.md). Утверждение о зелёном CI относится только к
указанному там SHA; локальные коммиты после него ещё могут не быть отправлены.

## Как проект сделан

API написан на Node.js, TypeScript, Fastify и `pg` с явным SQL; web — React и
Vite. PostgreSQL 16 хранит ограничения мест и уникальности, outbox связывает
изменение состояния с постановкой письма в транзакции, `LISTEN/NOTIFY` питает
live-экран. Mailpit заменяет внешнюю почту. Эти решения и причины выбора
пакетов записаны в [DEVLOG](docs/DEVLOG.md) и [спецификации](project_spec.md).

Работа велась с AI-агентами: сначала Claude Code CLI (Claude Opus 5.5),
для слайса 11 — Codex desktop (GPT-6). Агенты помогали реализовывать и
проверять небольшие слайсы; исходное ТЗ, решения, замечания, проверки и
временные отметки сохранены в DEVLOG и истории коммитов. Отдельный экспорт
сессий не включён. Чужое готовое решение не использовалось; Vite применён
как инструмент сборки, а код приложения создавался в репозитории.

Следующим заходом: согласовать и реализовать выбор часового пояса при
создании события, проверить текущий коммит в удалённом CI, разобрать
предупреждения `npm audit` и, перед реальным
развёртыванием, заменить демо-доступ по секретным ссылкам полноценной
аутентификацией и настроить почтовый провайдер.
