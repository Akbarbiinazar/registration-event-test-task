# План доказательств

Цель: каждое «ожидаемое поведение» из ТЗ доказывается **одним именованным
тестом** на реальной PostgreSQL. Тесты-доказательства лежат в
`apps/api/test/proofs/` и запускаются отдельно: `npm run test:proofs`.
Вспомогательные тесты (граничные случаи, инварианты БД) — рядом, в
`apps/api/test/`.

## Правила тестового стенда

1. **Реальная Postgres, без моков БД.** Тестовая база `events_test` в том же
   контейнере docker compose. Миграции применяются в `globalSetup`.
2. **Без БД тесты падают, а не пропускаются.** `globalSetup` подключается с
   таймаутом 3 с; при ошибке бросает
   `Error("Postgres недоступна на $TEST_DATABASE_URL — запустите npm run db:up")`.
   `it.skip`, `it.only`, `describe.skipIf`, `runIf` запрещены ESLint-правилами
   (`vitest/no-disabled-tests`, `vitest/no-focused-tests`) — lint падает.
3. **Часы инъектируются.** Доменный код получает `clock: Clock`; тесты
   используют `FakeClock` (`set(date)`, `advance(ms)`). ESLint запрещает
   `Date.now()` и `new Date()` без аргументов в `apps/api/src/domain` и
   `apps/api/src/jobs`. В доменных SQL-запросах нет `now()` — время приходит
   параметром.
4. **Изоляция.** Перед каждым тестом `TRUNCATE … RESTART IDENTITY CASCADE`.
   Файлы тестов выполняются последовательно (`fileParallelism: false`),
   параллелизм — только внутри теста, где он и проверяется.
5. **Инварианты после каждого теста.** `afterEach` вызывает
   `assertInvariants()` для всех событий: `seats_taken = count(confirmed)`,
   `seats_taken ≤ capacity`, «лист ожидания не пуст ⇒ мест нет».
6. **Письма проверяются по outbox** (контракт «письмо поставлено»). Отправку из
   outbox в SMTP проверяет отдельный тест с фейковым транспортом, а сквозной
   путь до Mailpit — smoke-скрипт.
7. **Конкурентность — настоящая:** пул `pg` на ≥ 25 соединений, запросы
   стартуют одновременно через `Promise.all`; сценарий гонки повторяется
   несколько раундов.
8. **Переход статуса и письмо проверяются вместе.** Для регистрации,
   постановки в лист ожидания, повышения и отказа сверять сохранённый статус с
   `kind` и `dedup_key` в outbox; повтор операции не должен добавлять письмо.
   При изменении регистрации, отказа или повышения повторно запускать P2,
   включая два одновременных отказа при двух ожидающих, и проверять FIFO,
   единственность повышения и счётчик мест.

## Доказательства (по одному на поведение)

### P1. Письмо с билетом; повторная регистрация не создаёт второго места
`proofs/p1-registration.proof.test.ts`

1. Событие на 5 мест. Регистрируем `Ann@Example.com`.
2. Ожидаем: статус `confirmed`; `seats_taken = 1`; в outbox ровно одно письмо
   `kind = 'ticket'` на `ann@example.com`, в теле — код билета регистрации.
3. Регистрируем `  ann@example.COM ` ещё раз, затем 10 раз параллельно.
4. Ожидаем: тот же `registration.id`; `seats_taken = 1`; одна регистрация;
   по-прежнему одно письмо.

Вспомогательные:
- прямой `INSERT` дубля в обход кода → `unique_violation` (I1 держит БД);
- прямой `INSERT` с `email` в верхнем регистре → `check_violation`;
- после отказа тот же email регистрируется заново как новая регистрация: новый
  `id`, новый код, новое письмо `ticket` (A4);
- регистрация после начала события проходит как обычно (A11);
- ответ на регистрацию не содержит кода билета (A3).

### P2. Лист ожидания и автоматическое повышение
`proofs/p2-waitlist.proof.test.ts`

1. Событие на 1 место. A, затем B, затем C.
2. Ожидаем: A `confirmed`; B и C `waitlisted`; B и C получили письмо
   `waitlisted`, билетов не получили.
3. A отказывается.
4. Ожидаем: A `cancelled`; **B** `confirmed` (не C — FIFO); у B ровно одно
   письмо `ticket`; C `waitlisted`; `seats_taken = 1`.

Вспомогательные:
- отказ ожидающего — повышения нет, мест не меняется;
- каждый отказ (из `confirmed` и из `waitlisted`) ставит ровно одно письмо
  `cancelled`; повторный отказ второго письма не ставит (A7);
- два подтверждённых отказываются **одновременно** при двух ожидающих → оба
  ожидающих повышены, каждый по одному разу, `seats_taken` не изменился (I8);
- отказ после начала события проходит, повышение работает (A11).

### P3. Два человека на последнее место
`proofs/p3-last-seat-race.proof.test.ts`

1. Событие на 1 место. 20 разных email регистрируются одновременно
   (отдельные соединения пула). Повторить 10 раундов на новых событиях.
2. Ожидаем в каждом раунде: ровно 1 `confirmed`, 19 `waitlisted`,
   `seats_taken = 1`, ровно 1 письмо `ticket`.
3. Отдельный кейс «ровно двое»: событие на 2 места, одно уже занято, двое
   регистрируются одновременно → 1 `confirmed` + 1 `waitlisted`.

Вспомогательные:
- прямой `UPDATE events SET seats_taken = capacity + 1` → `check_violation`
  (I2 держит БД, даже если код ошибётся);
- **регистрация в лист ‖ отказ (D1):** событие на 1 место, A `confirmed`, лист
  пуст. Одновременно регистрируется C и отказывается A; 50 раундов на новых
  событиях. Ожидаем в каждом раунде: C `confirmed` (сразу или повышением),
  `seats_taken = 1`, лист пуст. Без блокировки события в регистрации этот тест
  ловит «место свободно, а C в листе»;
- отказ подтверждённого ‖ новая регистрация при непустом листе → место уходит
  первому из листа, новый — в конец очереди.

### P4. Напоминание за сутки — ровно одно
`proofs/p4-reminder.proof.test.ts`

1. Событие стартует в `T`. Подтверждённые A, B; ожидающий C; отказавшийся D.
2. Часы = `T − 25 ч`, тик → напоминаний 0.
3. Часы = `T − 23 ч`, тик → ровно по одному `reminder` у A и B; у C и D нет.
4. Ещё тик, затем 5 тиков параллельно → новых писем нет.
5. Часы = `T + 1 мин`, тик → новых писем нет.

Вспомогательные:
- участник, повышенный из листа или зарегистрированный внутри 24-часового
  окна, получает одно напоминание на следующем тике (D6);
- после переноса на новую дату (`schedule_version` 2) и наступления окна —
  одно напоминание для новой даты (A8);
- **устаревшее напоминание не уходит (D4, I11):** напоминание поставлено, но
  не отправлено; участник отказался → тик мейлера ставит `skipped_at`,
  транспорт не вызван. То же, если событие перенесли (версия письма ≠ версии
  события);
- в тексте напоминания время в поясе события с подписью зоны (A13).

### P5. Чекин один раз; счётчик у организатора обновляется live
`proofs/p5-checkin-live.proof.test.ts`

1. Поднимаем настоящий HTTP-сервер на случайном порту. Событие, подтверждённый
   участник с кодом `K`.
2. Открываем **два** SSE-потока организатора (две «вкладки»), каждый получает
   снимок `checkedIn = 0`.
3. Чекин `K` через HTTP с ключом организатора → `200`.
4. Ожидаем: оба потока в течение 2 с получают снимок `checkedIn = 1`.
5. Повторный чекин `K` → `409 already_checked_in` с временем первого чекина;
   `checkedIn` остаётся 1.

Вспомогательные:
- 10 параллельных чекинов одного кода → ровно один `200` (I3);
- код ожидающего / отказавшегося → `409 ticket_not_active`; несуществующий
  код и код другого события → `404`;
- прямой `UPDATE` статуса чекиненного билета на `cancelled` → `check_violation`
  (I4);
- изменение, сделанное через **другое** соединение БД, тоже приходит в SSE
  (уведомления идут через Postgres, а не через память процесса).

### P6. Перенос события — письмо всем участникам
`proofs/p6-reschedule.proof.test.ts`

1. Событие на 2 места: подтверждённые A, B; ожидающий C; отказавшийся D.
2. Организатор переносит дату `T → T + 2 д`.
3. Ожидаем: `schedule_version = 2`; ровно по одному письму `rescheduled` у A,
   B, C; у D нет; в тексте старая и новая дата.
4. Повтор того же запроса (та же дата) → `200` с `unchanged: true`;
   `schedule_version` остаётся 2; новых писем нет (A9).
5. Второй перенос → ещё по одному письму каждому (всего по 2).

Вспомогательные:
- перенос в прошлое → `400` с сообщением «Нельзя перенести на прошедшее
  время»; без ключа / с чужим ключом → `401`;
- текст письма ожидающему отличается от текста участнику (D3);
- изменение только названия/описания писем не ставит.

## Вне тестов-доказательств

| Что | Чем доказывается |
|---|---|
| Отправка из outbox в SMTP, ретраи | `mailer.test.ts` с фейковым транспортом: успех → `sent_at`; ошибка → `attempts + 1`, `next_attempt_at` в будущем; `Message-ID` из `dedup_key`; устаревшее напоминание → `skipped_at` (см. P4) |
| Время в поясе события | `format.test.ts`: `formatInZone` для двух поясов, подпись зоны; создание события с невалидным `timezone` → `400` |
| Две вкладки браузера (требование 11) | P5 на уровне HTTP + Playwright E2E: организатор в одном контексте браузера, чекин в другом, счётчик меняется без перезагрузки |
| Письма реально доходят до Mailpit | `scripts/smoke.sh`: регистрация через API → письмо видно в API Mailpit |
| Каждый коммит зелёный | GitHub Actions: lint, typecheck, test (с сервисом postgres), build |
