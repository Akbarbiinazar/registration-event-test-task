| Качество | ESLint (typescript-eslint), `tsc --noEmit`, Prettier | |

## 2. Допущения

Подтверждены автором 2026-10-08 после гриля по трём веткам: модель данных и
инварианты, outbox/письма/напоминания, допущения. У каждого допущения указано
основание в ТЗ — цитата или «ТЗ молчит»: во втором случае это наше решение, и
выбран самый мягкий вариант, который не ломает остальные требования.

**Термин.** *Участник* — регистрация в статусе `confirmed`. Стоящий в листе
ожидания — не участник, но адресат письма о переносе (A9).

- **A1. Вход организатора.** Аккаунтов нет. Организатор при создании события
  получает секретную ссылку организатора (`/o/:eventId#key=<token>`); в БД
  хранится только SHA-256 токена. Этой же ссылкой открывается экран чекина.
  *Основание:* «Учётные записи и вход — на ваше усмотрение… можно обойтись без
  входа».
- **A2. Участник** не логинится. Управление регистрацией (билет, отказ) — по
  секретной ссылке из письма (`/t/:manageToken`). Почта не верифицируется:
  кто угодно может зарегистрировать чужой email — осознанное упрощение,
  последствия закрыты A3 и письмом об отказе (A7).
  *Основание:* то же; «Регистрация участника по email».
- **A3. Ответ на регистрацию не содержит билета** — только статус
  («место есть» / «вы в листе ожидания») и «проверьте почту». Иначе любой,
  введя чужой email, получил бы чужой код и прошёл бы чекин вместо владельца.
  Билет виден по ссылке из письма (в демо — в Mailpit; E2E берёт код через
  Mailpit API). (D7)
  *Основание:* «Зарегистрировавшийся получает **письмо** с билетом»; «Билет
  проходит чекин один раз».
- **A4. Повторная регистрация** того же email (A5) при активной регистрации
  (`confirmed` или `waitlisted`) возвращает текущий статус, **не создаёт места
  и не шлёт второе письмо**. После отказа можно зарегистрироваться заново —
  новой строкой, с новым билетом, в конец очереди, если мест нет. «Оживление»
  старой строки отвергнуто: ключ `ticket:{registration_id}` уже занят, письмо
  с билетом не ушло бы. (D2; сериализация — D1)
  *Основание:* «Повторная регистрация на тот же email не создаёт второго
  места».
- **A5. Нормализация email:** `trim` + `lower`. Gmail-точки и `+tag` не
  склеиваются.
  *Основание:* ТЗ молчит; нужна для «тот же email».
- **A6. Лист ожидания — FIFO** по `queue_seq`. Освободившееся место передаётся
  первому в очереди **в той же транзакции**, что и отказ, под блокировкой
  события (D1) — новый регистрант не может «перехватить» место между ними.
  *Основание:* «Кто-то отказался — первый из листа автоматически получает место
  и письмо».
- **A7. Письма:**
  | Письмо | Кому | Основание |
  |---|---|---|
  | Билет | при `confirmed` — сразу или после повышения из листа | «получает письмо с билетом», «получает место и письмо» |
  | «Вы в листе ожидания» | при `waitlisted` | ТЗ молчит: иначе регистрация при полном зале не оставляет следа в Mailpit |
  | «Отказ принят» | при отказе (из `confirmed` и из `waitlisted`) | ТЗ молчит: владелец узнаёт, если его ссылкой воспользовался кто-то другой; каждое действие видно в Mailpit |
  | Напоминание | участникам (A8) | «За сутки до события всем участникам приходит напоминание» |
  | Перенос | участникам и листу ожидания (A9) | «Организатор перенёс событие — все участники получают письмо» |
- **A8. Напоминание — ровно одно на участника на актуальную дату события.**
  Ставится тиком планировщика каждому `confirmed`, когда
  `starts_at − 24 ч ≤ now < starts_at`. Окно, а не точный момент: пропущенные
  тики догоняются. Кто получил место уже внутри окна (поздняя регистрация,
  повышение), получит напоминание на ближайшем тике — буквальное «всем
  участникам» важнее точного «за сутки». После переноса напоминание для новой
  даты ставится заново (это другая дата, другой ключ). Если между постановкой и
  отправкой регистрация перестала быть `confirmed` или дату перенесли, письмо не
  отправляется, а помечается `skipped_at`. (D3, D4, D6)
  *Основание:* «За сутки до события всем участникам приходит напоминание. Ровно
  одно».
- **A9. Перенос.** Письмо о переносе (старая → новая дата) получают участники
  **и** стоящие в листе ожидания — явное расширение: перенос меняет их решение
  «ждать ли место»; тексты писем разные. Отказавшимся — нет. (D3)
  Ограничения (ТЗ молчит, поэтому — с понятными сообщениями):
  - перенос на прошедшее время → ошибка «Нельзя перенести на прошедшее время»;
  - та же дата → не ошибка, ответ «Дата не изменилась, письма не отправлены»;
  - изменение названия/описания писем не порождает; в UI подпись «Участники
    получат письмо только при изменении даты».
  *Основание:* «Организатор перенёс событие — все участники получают письмо».
- **A10. Чекин** — ввод кода билета: 8 символов Crockford Base32 (цифры
  и латиница без `I`, `L`, `O`, `U`). Проходит только подтверждённый билет этого
  события, один раз. Код другого события = «не найден». Отменить чекин нельзя
  (повторный проход после отмены нарушил бы «один раз»). Ограничения по времени
  нет. Ввод терпимый: регистр не важен, пробелы и дефисы игнорируются, `O→0`,
  `I/L→1` (правило декодирования Crockford). В письме код показывается как
  `XXXX-XXXX`, в БД хранится каноническим (8 символов, верхний регистр).
  *Основание:* «Билет с кодом и экран чекина на входе. Сканер можно заменить
  вводом кода»; «Билет проходит чекин один раз». Формат и нормализация — ТЗ
  молчит.
- **A11. После начала события регистрация и отказ остаются открытыми.** На
  странице события — метка «Событие уже идёт». Опоздавший получает билет и может
  пройти чекин; отказ во время события повышает следующего из листа. Напоминания
  после начала не ставятся (окно A8 закончилось). Из списка предстоящих на
  главной событие уходит, по прямой ссылке доступно.
  *Основание:* ТЗ молчит; ограничение не защищает ни одного инварианта.
- **A12. Доставка писем — at-least-once** из outbox в SMTP: сначала отправка,
  потом отметка `sent_at`. «Ровно одно» гарантируется на уровне постановки в
  очередь (UNIQUE ключ). Дубль возможен только при падении процесса между
  отправкой и отметкой; чтобы почтовый клиент мог склеить дубль, `Message-ID`
  детерминированно выводится из ключа дедупликации. At-most-once отвергнут:
  письмо могло бы молча потеряться. (D5)
  *Основание:* «получает письмо с билетом», «напоминание… ровно одно».
- **A13. Часовой пояс события.** Время хранится в `timestamptz` (UTC). У
  события есть `timezone` — IANA-имя, которое берётся из браузера организатора
  при создании (`Intl.DateTimeFormat().resolvedOptions().timeZone`) и
  проверяется сервером через `Intl`. Везде — страница события, экран
  организатора, письма — время показывается в поясе события с подписью зоны:
  «18:00 (Москва, UTC+3)». Иначе организатор, поставивший 18:00, увидел бы в
  письме другое время.
  *Основание:* «Событие: описание, дата и время». Выбор пояса — ТЗ молчит.
- **A14. Интерфейс** на русском языке. *(вне веток гриля)*
- **A15. Один процесс API** выполняет HTTP, LISTEN, планировщик напоминаний и
  отправку почты. Конструкция безопасна и для нескольких экземпляров (UNIQUE,
  `FOR UPDATE`, `SKIP LOCKED`), но это не тестируется. *(вне веток гриля)*

### 2.1 Решения гриля

| # | Решение | Что нарушится в ТЗ при неверном ответе |
|---|---|---|
| D1 | Регистрация, отказ и перенос начинаются с `SELECT … FROM events WHERE id = $1 FOR UPDATE`; счётчик `seats_taken` + условный `UPDATE` + `CHECK` остаются страховкой. Закрывает гонку «регистрация в лист ‖ отказ»: в READ COMMITTED `UPDATE` с ложным `WHERE` строку не блокирует, отказ не видит незакоммиченного ожидающего и освобождает место — место свободно при непустом листе | «Кто-то отказался — первый из листа автоматически получает место»; «Два человека на последнее место…» |

## 3. Поведение

Время везде берётся из инъектируемых часов `Clock` (см. §6), не из
`Date.now()` и не из SQL `now()`.

### 3.1 Событие
- Организатор создаёт событие: название (1–200 симв.), описание, дата/время
  начала (в будущем; вводится в поясе браузера организатора), лимит мест
  (1–10 000). Вместе с событием сохраняется `timezone` организатора (A13). В
  ответ — публичная ссылка и секретная ссылка организатора (показывается один
  раз).
- Публичная страница события: описание, дата в поясе события с подписью зоны,
  «осталось мест N» или «мест нет, можно встать в лист ожидания»; после начала —
  метка «Событие уже идёт» (A11).
- Список предстоящих событий на главной (только для удобства демо).

### 3.2 Регистрация и отказ
Каждая операция — одна транзакция, которая начинается с блокировки строки
события `FOR UPDATE` (D1).

- **Дано** событие со свободными местами, **когда** участник вводит email,
  **тогда** он получает статус `confirmed`, занятые места +1, в outbox
  появляется письмо с билетом (код + ссылка на билет). В ответе — статус, без
  билета (A3).
- **Дано** у email уже есть активная регистрация на это событие, **когда** он
  регистрируется снова (в любом регистре), **тогда** возвращается существующий
  статус, мест и писем не добавляется.
- **Дано** подтверждённая регистрация, **когда** участник отказывается по
  ссылке, **тогда** статус `cancelled`, в outbox — письмо «отказ принят», и
  (§3.3) место переходит первому из листа ожидания или освобождается.
- Отказ из листа ожидания убирает из очереди и тоже ставит письмо «отказ
  принят».
- Регистрация и отказ доступны и после начала события (A11).
- Чекиненный билет отменить нельзя.

### 3.3 Лист ожидания
- **Дано** все места заняты, **когда** регистрируется новый email, **тогда**
  статус `waitlisted`, письмо «вы в листе ожидания», места не меняются.
- **Дано** в листе ожидания B, затем C, **когда** подтверждённый A
  отказывается, **тогда** в той же транзакции B получает `confirmed` и письмо с
  билетом; счётчик занятых мест не меняется; C остаётся в очереди.
- **Дано** мест нет, **когда** одновременно C регистрируется (попадает в лист),
  а подтверждённый A отказывается, **тогда** в любом порядке коммита свободных
  мест при непустом листе не остаётся: либо C получает место A, либо C
  повышается из листа (D1).
- Инвариант: если лист ожидания не пуст, свободных мест нет.

### 3.4 Гонка за последнее место
- **Дано** одно свободное место, **когда** два (или двадцать) разных email
  регистрируются одновременно, **тогда** ровно один `confirmed`, остальные
  `waitlisted`; превышение лимита невозможно даже при ошибке в коде (CHECK).

### 3.5 Напоминание
- Планировщик каждые `REMINDER_TICK_MS` (по умолчанию 60 с) выполняет тик.
- **Дано** `starts_at − 24 ч ≤ now < starts_at`, **когда** выполняется тик,
  **тогда** каждому подтверждённому участнику ставится одно напоминание на
  текущую `schedule_version`. Повторные и параллельные тики новых писем не
  создают. Пропущенные тики догоняются, пока событие не началось.
- Получивший место внутри окна получает напоминание на ближайшем тике.
- Стоящим в листе ожидания и отказавшимся напоминание не ставится.
- **Дано** напоминание поставлено, но не отправлено, **когда** участник
  отказался или событие перенесли, **тогда** мейлер не отправляет его, а ставит
  `skipped_at` (D4).

### 3.6 Чекин и live-счётчик
- Экран чекина: поле ввода кода → результат: «пропущен ✓», «уже прошёл в
  HH:MM», «билет не найден», «билет не активен (лист ожидания / отказ)».
- Ввод нормализуется перед поиском: регистр, пробелы, дефисы, `O→0`, `I/L→1`
  (A10).
- Код от другого события = «не найден».
- **Когда** чекин успешен, **тогда** экран организатора во всех открытых
  вкладках обновляет «пришло» без перезагрузки (SSE); то же для
  «зарегистрировано» и «в листе ожидания» при регистрации/отказе.

### 3.7 Перенос события
- **Когда** организатор меняет дату начала на будущую и отличную от текущей,
  **тогда** под блокировкой события (D1) `schedule_version` +1, и в той же
  транзакции каждому подтверждённому и ожидающему ставится письмо о переносе
  (старая → новая дата, в поясе события; разные тексты для участника и
  ожидающего).
- Дата в прошлом → ошибка «Нельзя перенести на прошедшее время».
- Та же дата → успешный ответ «Дата не изменилась, письма не отправлены»,
  `schedule_version` не меняется.
- Изменение названия/описания писем не порождает.

## 4. Модель данных

```sql
events
  id                   uuid PK
  title                text NOT NULL            CHECK length 1..200
  description          text NOT NULL DEFAULT ''
  starts_at            timestamptz NOT NULL
  timezone             text NOT NULL            -- IANA, напр. 'Europe/Moscow' (A13)
  capacity             int  NOT NULL            CHECK (capacity BETWEEN 1 AND 10000)
  seats_taken          int  NOT NULL DEFAULT 0  CHECK (seats_taken BETWEEN 0 AND capacity)
  schedule_version     int  NOT NULL DEFAULT 1
  organizer_token_hash text NOT NULL
  created_at, updated_at timestamptz NOT NULL

registrations
  id               uuid PK
  event_id         uuid NOT NULL FK → events
  email            text NOT NULL   CHECK (email = lower(btrim(email)))
  status           text NOT NULL   CHECK (status IN ('confirmed','waitlisted','cancelled'))
  queue_seq        bigint GENERATED ALWAYS AS IDENTITY   -- порядок листа ожидания
  ticket_code      text NOT NULL UNIQUE                  -- канонический, 8 симв. Crockford
  manage_token     text NOT NULL UNIQUE                  -- см. ниже, почему не хэш
  created_at       timestamptz NOT NULL
  confirmed_at     timestamptz NULL
  cancelled_at     timestamptz NULL
  checked_in_at    timestamptz NULL
  CHECK ((status = 'cancelled') = (cancelled_at IS NOT NULL))
  CHECK (checked_in_at IS NULL OR status = 'confirmed')
  UNIQUE INDEX one_active_per_email ON (event_id, email) WHERE status <> 'cancelled'
  INDEX waitlist_order ON (event_id, queue_seq) WHERE status = 'waitlisted'

outbox_emails
  id               bigint GENERATED ALWAYS AS IDENTITY PK
  dedup_key        text NOT NULL UNIQUE
  kind             text NOT NULL CHECK (kind IN ('ticket','waitlisted','cancelled','reminder','rescheduled'))
  registration_id  uuid NOT NULL FK → registrations
  schedule_version int  NULL                   -- для reminder: версия даты, на которую поставлено
  to_email, subject, body_text   text NOT NULL   -- письмо рендерится при постановке
  created_at       timestamptz NOT NULL
  next_attempt_at  timestamptz NOT NULL
  attempts         int NOT NULL DEFAULT 0
  last_error       text NULL
  sent_at          timestamptz NULL
  skipped_at       timestamptz NULL            -- устаревшее напоминание, не отправлено (D4)
  CHECK (kind <> 'reminder' OR schedule_version IS NOT NULL)
  CHECK (NOT (sent_at IS NOT NULL AND skipped_at IS NOT NULL))
```

Ключи дедупликации писем:

| Письмо | `dedup_key` | Следствие |
|---|---|---|
| Билет (сразу или после повышения) | `ticket:{registration_id}` | Не больше одного билета на регистрацию |
| Лист ожидания | `waitlisted:{registration_id}` | |
| Отказ принят | `cancelled:{registration_id}` | Отказ — однократный переход статуса |
| Напоминание | `reminder:{registration_id}:{schedule_version}` | Ровно одно на актуальную дату (A8) |
| Перенос | `rescheduled:{registration_id}:{schedule_version}` | Одно на каждый перенос |

`manage_token` хранится открытым, в отличие от токена организатора: письма о
повышении и переносе формируются позже регистрации и должны содержать ссылку.
Хэш не позволил бы её восстановить.

## 5. Инварианты, которые обеспечивает БД, а не код

| # | Инвариант | Механизм в Postgres |
|---|---|---|
| I1 | Одна активная регистрация на (событие, email) | Частичный `UNIQUE (event_id, email) WHERE status <> 'cancelled'` + `CHECK email = lower(btrim(email))`; вставка `ON CONFLICT DO NOTHING` |
| I2 | Мест не больше лимита | Условный `UPDATE events SET seats_taken = seats_taken + 1 WHERE id = $1 AND seats_taken < capacity RETURNING` + `CHECK (seats_taken <= capacity)` как страховка |
| I3 | Билет проходит чекин один раз | `UPDATE registrations SET checked_in_at = $now WHERE ticket_code = $1 AND event_id = $2 AND status = 'confirmed' AND checked_in_at IS NULL RETURNING` |
| I4 | Чекин только у подтверждённого; чекиненный нельзя отменить | `CHECK (checked_in_at IS NULL OR status = 'confirmed')` |
| I5 | Каждое письмо ставится в очередь не более одного раза | `UNIQUE (dedup_key)` + `INSERT … ON CONFLICT DO NOTHING` |
| I6 | Письмо ставится тогда и только тогда, когда изменение состояния зафиксировано | Outbox: вставка в той же транзакции |
| I7 | Live-уведомление только о зафиксированных изменениях | `pg_notify('event_stats', event_id)` внутри транзакции — доставляется после `COMMIT` |
| I8 | Все решения о местах и очереди по одному событию сериализованы; каждый ожидающий повышается не более одного раза, FIFO | Регистрация, отказ и перенос начинают транзакцию с `SELECT … FROM events WHERE id = $1 FOR UPDATE` (D1); порядок — `queue_seq` (identity, не время — нет ничьих) |
| I9 | Коды билетов и токены уникальны | `UNIQUE` |
| I10 | Конкурентный тик напоминаний не дублирует | `INSERT … SELECT … ON CONFLICT (dedup_key) DO NOTHING` одним запросом |
| I11 | Устаревшее напоминание не отправляется | Мейлер в той же транзакции, где забирает письмо `FOR UPDATE SKIP LOCKED`, сверяет `outbox.schedule_version = events.schedule_version` и `registrations.status = 'confirmed'`; иначе `skipped_at = $now` |

Что держится **кодом**, а не БД (честно):
- `seats_taken = count(status = 'confirmed')` — поддерживается в одной
  транзакции с изменением статуса. Проверяется хелпером `assertInvariants()`
  после каждого теста, не триггером.
- «Если лист ожидания не пуст — свободных мест нет» — держится тем, что все
  записи по событию идут под блокировкой его строки (D1, I8), и повышением в
  транзакции отказа (A6). Проверяется тем же хелпером.

Уровень изоляции — `READ COMMITTED` (по умолчанию); корректность держится на
блокировке строки события (`FOR UPDATE`) и условных `UPDATE`, а не на
`SERIALIZABLE` с ретраями.

## 6. Архитектура backend (кратко)

- `modules/*` — граница `controller → service → repository`: контроллер
  валидирует HTTP и задаёт контракт, сервис содержит доменную операцию вида
  `register(deps, input)`, repository выполняет SQL. Это согласовано для
  слайса 03, чтобы продолжить структуру уже реализованных модулей 01–02.
  Каждая операция изменения состояния — одна транзакция: блокировка события
  (если операция пишет по событию) → изменение состояния → outbox → `pg_notify`.
- `Clock { now(): Date }`: `SystemClock` в проде, `FakeClock` (`set`, `advance`)
  в тестах. Время передаётся в SQL параметром `$now`.
- `jobs/reminders.ts` — `runReminderTick(deps)`; `setInterval` только в
  `main.ts`. Тесты вызывают тик напрямую.
- `jobs/mailer.ts` — `runMailerTick(deps, transport)`: забирает пачку
  `FOR UPDATE SKIP LOCKED`; напоминания сверяет с текущей версией события и
  статусом регистрации, устаревшие помечает `skipped_at` (I11); остальные шлёт и
  ставит `sent_at`; ошибка → `attempts + 1`, `next_attempt_at` с backoff.
- Форматирование времени для писем и UI — одна функция `formatInZone(at,
  timezone)` с подписью зоны (A13).
- `live/*` — один выделенный `pg.Client` с `LISTEN event_stats`, раздаёт
  подписчикам SSE (`GET /api/organizer/events/:id/stream?key=…`). При
  подключении сразу шлётся снимок, далее — снимок после каждого NOTIFY.
- HTTP-слой тонкий: валидация (TypeBox) → доменная функция → маппинг ошибок.

## 7. Сознательно не делаем

| Не делаем | Почему / чем заменено |
|---|---|
| Аккаунты, пароли, верификация email | A1/A2: секретные ссылки. Для демо достаточно, для прода — нет |
| Сканер QR | Разрешено ТЗ; ввод кода. Возможно, QR-картинка в билете, если останется время |
| Изменение лимита мест, удаление/отмена события | Не требуется ТЗ; увеличение лимита потребовало бы массового повышения из листа |
| Отмена чекина | Не требуется; нарушила бы «один раз»; запрещено CHECK'ом (I4) |
| Время окончания события, закрытие регистрации | ТЗ не требует (A11) |
| Реальный почтовый провайдер, exactly-once доставка | Mailpit по ТЗ; доставка at-least-once (A12) |
| Rate limiting, капча, защита от спама регистрациями | Вне объёма тестового |
| Масштабирование на N экземпляров API | Конструкция допускает, но не тестируется (A15) |
| Пагинация, поиск, i18n | Объём демо |
| Продакшн-деплой, HTTPS | Только локальный запуск по ТЗ |
